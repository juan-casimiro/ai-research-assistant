# Generate corpus metadata and download PDFs

Given PMCIDs, use the existing helpers to fetch metadata, check article licences,
download readable PDFs and write `data/corpus_manifest.json`. Read AGENTS.md and
work in the assigned checkout. The generate-corpus-metadata skill routes here.

## 1. Prepare the inputs

Use a new ignored `build/corpus/<run-id>/` directory for all temporary files:

```sh
corpus_run_dir="build/corpus/<unique-run-id>"
mkdir -p build/corpus
mkdir "$corpus_run_dir"
mkdir "$corpus_run_dir/metadata" "$corpus_run_dir/provenance" "$corpus_run_dir/pdfs"
```

Resolve each PMCID and explicitly choose its PMC deposit version using the
[PMC ID Converter](https://pmc.ncbi.nlm.nih.gov/tools/id-converter-api/) and the
versioned article record. Do not assume version 1 or silently select latest.
Choose a title-based filename: PMCID plus 1–7 lowercase hyphen-separated words
and `.pdf`. Match the actual title and study type, not inherited filenames.
The article `id` is the filename without `.pdf`.

Generate local `candidates.json` with an `articles` array. Each entry contains
`pmcid`, `pmc_version`, `filename`, `cluster` (topic), and `search_query`.
Preserve a supplied discovery query; if none exists, record
"User supplied PMCID; original discovery query unavailable". Do not invent one.
This intermediate file is generated by the skill and is not committed.

## 2. Fetch and check metadata

For each article, replace the placeholders and run:

```sh
.venv/bin/python fetch_article_metadata.py --pmcid <PMCID> --pmc-version <VERSION> \
  --search-query '<query or explicit selection provenance>' \
  --filename <PMCID-descriptive-title.pdf> --cluster <TOPIC> \
  --output "$corpus_run_dir/metadata/<PMCID>.<VERSION>.json" \
  --archive-dir "$corpus_run_dir/provenance"
```

The helper checks PMC/PubMed/ID Converter identity, pinned versions, retractions
and available XML checksums. Before including an article, verify:

- PMCID, pinned version, DOI and numeric PMID are present and agree.
- Title, ordered authors, journal and publication date are present. Keep date
  precision; never invent missing month/day values.
- The complete PubMed abstract is present, retaining labelled sections in its text.
- Licence evidence shows exactly CC BY 4.0 or CC0 1.0: keep `license`,
  `license_notes` and exact `licence_urls`. Confirm the pinned article notice;
  PMC access or an ambiguous generic BY label alone is insufficient.

Missing mandatory values, retractions or unresolved licence conflicts mean the
article is excluded from the manifest. Record failures in a local run log.
The helper may return missing/unsupported values; a successful exit is not a
substitute for these checks.

The manifest keeps only article identity/filename/topic, bibliography, abstract,
licence evidence and PMC/PubMed source links. Metadata source responses may stay
local for checking; no review inventories or eligibility-status schema is needed.

## 3. Download and check PDFs

Combine the passing article records into a local `acquisition.json` envelope:
`{"articles": [<records>]}`. Then run:

```sh
.venv/bin/python download_corpus.py --manifest "$corpus_run_dir/acquisition.json" \
  --corpus-dir "$corpus_run_dir/pdfs"
```

The downloader resolves pinned PMC Cloud metadata/PDF objects, checks DOI/PMCID,
available MD5 and PDF structure, and removes failed partial downloads. All new
articles must use this automatic PMC route; the legacy manual fallback is for V1.

Check each file has nonzero pages, readable text and a first-page title matching
the metadata. Check article licence notices if present; unresolved disagreement
with the source licence fails inclusion. Use pypdf for text checks and render a
page when text is insufficient to confirm identity. Readable existing files are
skipped by the downloader, so check their identity rather than assuming a skip
means the right article. Report missing/failed files instead of dropping them
silently. PDFs and raw acquisition files remain untracked.

## 4. Write or complete the manifest

For a **new output**, give the builder only candidates that passed the metadata,
licence and PDF checks:

```sh
.venv/bin/python build_corpus_manifest.py --candidates "$corpus_run_dir/candidates.json" \
  --output data/corpus_manifest.json
```

The builder refetches metadata and refuses an existing output. Check the resulting
records against the verified identities, abstracts and licences; changed source
content must be checked again. The manifest goes directly to its final path.

For an **existing manifest**, skip the builder. Read its records and complete or
correct the necessary fields in place after the same checks. Do not delete the
file or refetch all articles just to bypass overwrite protection. For additions,
fetch/check the new records and append only passing, unique articles, preserving
existing records. Preserve frozen V1 data and scientific content.

To avoid refetching, an agent may also assemble a new final manifest directly
from the already fetched and verified article JSON records, using the same
`{"articles": [...]}` envelope. No extra manifest-finalisation tool is required.

## 5. Verify and report

Check unique PMCIDs, IDs and filenames; mandatory metadata and accepted licences
for every member; and one matching readable PDF per manifest article. Retain full
citation, article links and licence notices for attribution. Report included and
excluded articles, failed checks and manifest/PDF locations. The checks cover
this MVP's metadata, article text and local PDF use; they do not authorise public
PDF distribution or reuse of separately credited material.

Helper regressions (offline, no article downloads or LLM calls):

```sh
.venv/bin/python -m unittest tests.corpus.test_download_corpus tests.corpus.test_fetch_article_metadata tests.corpus.test_build_corpus_manifest -v
```
